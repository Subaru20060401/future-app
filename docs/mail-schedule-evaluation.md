# メール予定抽出の再評価手順

予定抽出にAI APIは使用しない。本番の readScheduleMail、scanScheduleMails、AppState を使って、取得済みの同じメールを繰り返し評価する。

## データの置き場所

実メール・本文・評価結果は .dart_tool/mail_schedule_eval/ 内だけに置く。このディレクトリはGit管理外。本文をテストコードや公開用docsへ貼らない。

入力は tools/evaluate_mail_schedule.dart が扱うJSON配列で、id / threadId / internalDate（Unixミリ秒文字列）/ subject / from / payload を持つ。payload は mimeType / body / parts の再帰構造。body は Gmail API の data（base64url）、または接続済みGmailツールの content / base64_url_content を受け付ける。接続ツールのメールはヘッダー名等をこの形式に変換してから保存する。

取得はアプリの fetchScheduleMails と同じ件名検索条件で行う。評価時点・期間・ページの取り切れを記録する。接続済みGmailツール経由の取得は、スマホのトークン・通信そのものの再現ではない。スマホの登録済みデータを使う場合も、専用の検証コピーにする。

## 実行

プロジェクトのルートで実行する。

    dart tools/evaluate_mail_schedule.dart .dart_tool/mail_schedule_eval/input-all.json .dart_tool/mail_schedule_eval/after.json 2026-10-25T21:30:00
    flutter test test/mail_schedule_replay_test.dart
    python tools/render_mail_schedule_report.py

変更前の同じ評価結果は before.json として保存しておく。レポートは before.json / after.json / app-result.json から report.html を生成する。初回に基準がない場合は、after.jsonのコピーをbefore.jsonにして比較基準を作る（変更前の実測とは呼ばない）。

replayテストは after.json に含まれる本文を本番の取り込みサービスへ渡す。初回30日、過去予定除外、取消照合、確認待ち、再取得による重複の有無を検証する。予定やシフトを承認せず、GmailやGoogleカレンダーへ書き込まない。データがない環境ではこのテストをスキップする。

基準日時は評価したい日本時間の暦で指定する。レポート生成時の日時・規則版・件数表示は、その評価結果と一致させる。

## 改善の進め方

1. 全件を読み取り、確認待ち・過去・取消履歴・対象外の理由を出す。
2. report.html で「予定として必要」「不要」「取消・変更として必要」を人が評価する。手動評価はJSONへ保存し、次の規則版で読み込める。「手動評価と不一致」だけの絞り込みも使える。
3. 誤検出だけでなく、除外された必要な予定も確認する。件数が減っただけで精度が上がったと判定しない。
4. 誤りの書き方を架空化し、個人名・メールアドレス・予約番号・URLを残さず回帰テストへ追加する。
5. 同じ実メールで変更前後を比較する。画面に評価済み・一致・不一致・不要な抽出・見逃しを集計する。抽出単位で比べるため、過去・重複でも本人の予約なら「予定として必要」にする。未評価は正解扱いにしない。日時の正誤は別途本文と照合する。
6. flutter test / flutter analyze lib/ を実行する。公開する場合はWebビルドと実機確認も行う。

## 規則版と保存済み候補

- 規則を変えたら mail_schedule_models.dart の kScheduleRulesVersion を更新する。ScheduleSuggestion の既定値と読み取り側は同じ定数を使う。
- 規則版が変わると、次の取り込みは直近30日を再解析する。取得失敗・件数上限時は版の適用完了を記録しない。
- 旧版の未操作の確認待ちは起動・インポート・取り込み時に履歴へ下げる。
- 登録済み、本人が保留・却下したもの、見本は自動整理で変更しない。
- 取消は登録対象がある場合だけ確認待ちへ出す。対象がなければ照合履歴に残し、古い予約メールの再提案を防ぐ。
- 不要と判断した同じ予約のリマインドは、別メールIDでも再提案しない。変更・取消は追加とは別に扱う。
- 同じ取得内で取消に置き換わった候補は「見つかった件数」に含めない。
- 見本は設定の「見本の提案を消す」から整理できる。実メールの評価には見本を含めない。

## 今回の確認範囲と残る制約

2026年10月25日に、同じ検索条件のメール138通を取得した。基準日時から正確に30日内の133通を本番サービスで評価した（Gmailの日付検索は日単位のため、取得範囲と完全一致しない）。抽出段階は規則版2で45件、版3で13件、版4で15件。版4の15件は将来の予約3件（うち同一予約の別メール1件）、過去予約9件、取消3件。空の登録状態での確認待ちは2件になった。実データの詳細はGit管理外のレポートを参照する。

版4では、対応する国内線の旅程表と予約確認メールから便名・出発地・到着地・それぞれの日付と時刻を読む。発行日・予約日を出発日にしない。同じ送信元ドメインと予約番号のメールは1件にまとめ、取消も同じ予約番号で照合する。未購入、日付と曜日の不一致、壊れた時刻、到着が出発より前の旅程は対象外とする。国内の対応空港8か所・単一区間・2種類の本文構造に限定している。

通常の予約では、取消・変更の条件文や否定文を実行済みとして扱わない。ISO形式の日付、日本語の分表記にも対応し、10:3、110:00、終了11:99などの壊れた時刻を部分一致で補完しない。勤務時間の欄だけあって時刻が読めないシフトも追加しない。

これは人が全件を正解付けした精度測定ではない。以下は追加検証が必要。

- スマホ側の既存予定・承認履歴と照合した結果。
- 検索対象外の件名、宣伝カテゴリに誤分類された予約。
- 文字化け・特殊な旅程表・画像や添付の中だけにある日時。
- 国際線、未対応の国内空港、往復・乗継など複数区間の旅程。海外現地時刻を日本時間と推測しないため対象外。
- 終了時刻が書かれていない確定予定（開始は読める場合に候補として残り、承認前に補う）。
- 日付のみのメールは、終日の明示がない場合には候補にしないため、必要な予定を見逃す可能性がある。

実メールで文字化けした未購入の航空予約や、日時がマイページにしかないリマインドもあった。これらを推測で予定化しない。必要な予定をすべて拾える段階とは断定しない。
