## 1.5 GPT 実装レビュー（83d9ca5）への対応（2026-11-20）

レビュー文書は `docs/gpt-implementation-review.md`、再現テストは `test/reviewer_concurrency_test.dart`（受け取ったまま配置。
期待値は変えていない）。3 件とも修正前に落ち、修正後に通ることを確認した。周辺のテストは `test/save_paths_test.dart`。

| 指摘 | 原因 | 修正 |
|---|---|---|
| P1 保存中のカード設定変更が古い値で上書きされる | カード設定だけ `_writeCardDays` で SharedPreferences に直接書き、保存の列（`_enqueueWrite`）を通っていなかった | カード設定の保存（引落日・締め日・外す・名前の変更・まとめ）を `saveData` に一本化。家計データのキーを書く入口は `saveData` だけ。`_saveDriveSyncState` も `saved_data_updated_at` を書かないようにした |
| P1 Drive 取り込みの保存中の編集が同期済みになる | 取り込み完了時の時刻を `driveSyncedAt` にしていた | 取り込みを**始める前**の時刻を同期済みの基準にする。変更時刻・基準時刻は `issueStamp()` で必ず増える値にした（時計が同じ値を返しても、取り込み後の編集は基準より後になる） |
| P2 保存先の false を成功扱いする | `setX`・`remove` の `Future<bool>` を見ていなかった | 保存・削除はすべて `_checked` を通し、false も失敗として扱う（復旧点・一時記録・本体の各キー・記録の削除・起動時の書き戻し） |

あわせて、保存の列は「後ろに並んだ保存が終わるまで待ってから完了」にした（`saveData` が返った時点で、それまでの変更が端末に入っている）。

確かめたこと（`save_paths_test.dart`）: カード設定 4 種類の変更を保存の途中で行っても再起動後に残る／後ろに並んだ保存が途中で止まっても、
次の起動で新しい設定に整う（一時記録が新しい設定を巻き戻さない）／時計が止まっていても取り込み中の編集は未同期／取り込みが失敗したら
同期済みにせず、端末とメモリが同じ状態／false を返す段階ごと（復旧点・一時記録・本体・削除・起動時の書き戻し）。

💡 この版で残した「取り込みが失敗すると、取り込み中の編集が一緒に消える」は、次の §1.6 で直した（取り込み中は編集を受け付けない）。

⚠️ 家計データ以外の端末ごとの設定（表示・通知・同期の状態など）と、起動時の読み込み中だけ行う 2 つの書き込み（初回のカードの種・
古い給料の記録の移行）は、今も直接書いている。家計データのキーとは重ならない／保存が始まる前に行う。

バンドルについて: この作業環境のリポジトリは履歴の浅いクローン（shallow）だったため、前回のバンドルは過去のコミットの親が欠けていた。
`git fetch --unshallow` で全履歴を取得し、`HEAD` も含めて作り直した（`git bundle create … HEAD claude/zen-heisenberg-xq1194`）。
通常の `git clone` で開けて最新のコミットが取り出せること、`ea60eca` があること、`git fsck` が通ることを確かめた。
⚠️ 全履歴には、以前から公開されている古いコミット（2026-09-05 の 3 件）の作者欄と、過去の `docs/gmail_setup.md` の差分に

⚠️ 受け付けてから巻き戻すと「入力できたのに消えた」になる。変更は始める前に断る。

| 経路 | 取り込み中の扱い | 場所 |

  バックアップの復元・貼り付けは `importJson` が自分で持つ。成功でも失敗でも `finally` で外し、覆いが消えてそのまま操作できる

- 取り込みの自己修復（`repairData`）から呼ぶ `cleanupInstallmentDuplicates` は断らない（保存しない修復のため）
- 通知（`notifyListeners`）は鍵を取るときと外すときの 2 回（取り込んだ内容での表示し直しは、鍵を外すときにまとめた）

テスト（`test/import_lock_test.dart`）: 取り込みの保存が失敗するときの編集は断られ、失敗のあとは取り込む前の内容でそのまま編集・保存できる／
ドライブからの取り込みの失敗でも同じ／取得を待っている間から止める／二重の取り込み／取り込み中はドライブへ保存しない／
先に走っていた保存が終わってから復旧点を書く（`_drainWrites` を外すと落ちることを確認）／Gmail の反映は取り込み後に行う／
鍵が外れた直後に次の取り込みが始まっても待つ／鍵を持つ処理が例外でも外れる／画面: 覆って押せず、成功・失敗のどちらでも戻る。

変えたテスト（編集を断る仕様にしたため）: `reviewer_concurrency_test.dart` の 1 件目と `save_paths_test.dart` の

## 2. 目的と新しい設計

目的は「1 か所を直すと別の画面の金額が静かに変わる」を構造で起きにくくすること。全面書き換えはしていない。

- 画面の窓口は今までどおり `AppState`（provider + ChangeNotifier）
- 純粋な部品は AppState の外。依存は `AppState → finance / models` の一方向（`test/architecture_test.dart` で検査）
  - `lib/models/`: データ型と JSON（移動のみ。`app_state.dart` から再 export）
  - `lib/finance/billing_dates.dart`: 月末へのそろえ・翌営業日の引落日・締め期間・利用日の引落月
  - `lib/finance/forecast.dart`: 予想の行（`ForecastLine`）と月（`MonthForecast`）、最低残高・足りない日
- 予想は `AppState.forecastMonths` の行から、月末・内訳・日ごとの並び・最低残高・足りない日・次の引き落とし・収支の内訳を作る
- 「今日」は `AppState(clock:)`（`clockNow()`）
- 金額の意味は 3 つ（`docs/architecture-plan.md` §11）: ① 利用月の支出 ② 支払日の入出金 ③ 残高の予想（②のうち残高を書いた日より後）
- **請求の月**（何月の請求か）と**実際の引落日**は別の概念。決めるのは `billMonthOf` 1 か所
- **保存**は「全部そろったときだけ有効」: 一時保存 → 全キー → 一時保存を消す。取り込みは取り込む前の状態を復旧点に残してから

## 6. 保存データの互換性と移行

## 9. 未検証のこと・既知の問題・残っている懸念

### 実環境で確かめていないもの

- **Google 連携（Gmail・Drive・Calendar）は実アカウントで動かしていない。** Drive は偽の `DriveStore` でのテストだけ。
  `GoogleDriveStore` は旧 `fetch`/`upload` を移したもので、実際のドライブでの読み書きは要確認
- **iOS・Android はビルドしていない**
- Web の localStorage で実際に容量が足りなくなったときの動き（例外の種類・一時保存が書けないとき）は、テストの偽のストアでだけ確かめた
- 実データでの見え方（明細の多い月、長いカード名、判定できない銀行確定がどれくらい出るか）

### 既知の問題・判断して残したもの

- 引落日の設定が無いカードの銀行確定は、請求の月を照らし合わせられないので日付の月で扱う（2 月末などで翌月にずれると、
  取り違えが残りうる。引落日を設定すれば判定に乗る）
- 請求予定（billing）の明細は、利用月の支出では日付の月の利用として数えている（変更前から。今回は変えていない）
- 残高を一度も書いていないときの給料の入金月は最頻値の締め（`paydayOffsetMonths`）で計算する（変更前のまま）
- 年間支出の「うち設定から計算」には、アプリを使う前の月の定期も入る（定期に開始日が無いため）。推定であることは表示している
- `thisMonthBreakdown` などの Map 版の内訳は、画面では使わずテストだけが使う（互換のため残した）
- `MainNavigationScreen` が足すリスナーは外していない（変更前のまま）
- 明細の ID は取り込みのたびに作り直される（変更前のまま）
- 取り込み中は、家計データ以外の端末ごとの設定（表示・通知など）も画面の覆いで操作できない（AppState では断っていない）
- 取り込み中に Gmail の取得が終わると、反映は取り込みのあとになる（取り込んだ中身に、メールを正本として反映し直す）。
  カレンダーに作った予定の記録も同じく取り込みのあと。取り込みで置き換わったシフト・予定の記録は付けない（シフトは作った予定を消す）
- 保存の一時保存のため、保存のたびに全データを 2 回書く。データが大きいと遅くなる可能性がある（実測していない）
- Flutter の `material_ui` への移行は別作業（ユーザーと合意）
- `GmailService` から解析を分ける作業（計画の「任意」）はしていない
- `pubspec.lock` は、この環境の Flutter で `pub get` すると SDK 同梱パッケージの版が変わるが、コミットしていない

### レビューで特に見てほしいところ

- 取り込み中に家計データを書き換える経路で、`_ensureEditable` も `runWhenEditable` も通らないものが無いか
  （保存する公開メソッドはテストで確かめている。保存しない書き換え・画面からの直接の書き換えは安全網だけ）
- `_recoverInterruptedWrite` と `importJson` の組み合わせ（復旧点・一時保存・指紋の照合）が、途中のどの時点で止まっても
  整った状態に戻るか。テストに無い止まり方が無いか
- `_enqueueWrite` で保存をまとめるとき、まとめた値が「同じ瞬間の状態」でなくなる場合が無いか（後の値で上書きしている）
- `billMonthOf` の判定（候補が一意のときだけ）と、それを使う箇所に漏れが無いか（`PaymentSource.bank` を参照する箇所）
- `drawReflectionOf` の推定（同じ日は判断できない）と、確認画面の基本の操作
- `forecastMonths` の振り分け（前月分の行・今月以前にずれた行の扱い）
