# メールから予定・単発バイトを提案する機能：実装計画

作成日：2026-10-25（日本時間）  
状態：計画書。機能実装・実メールのAI解析・課金設定・デプロイは未実施。デプロイは別担当。  
対象：ポケットメイドのWeb版。GalaxyのChrome／PWAとWindowsを主な確認環境にする。

## 1. 今回決めたこと

**Gmailから予約・説明会・面接・単発バイトのメールを見つけ、内容を確認してから予定やシフトとして登録する。** 初版の対象は本人確認済み。提出・支払などの締切を「やること」に登録する機能は次の段階に分ける。

前の[機能追加・改善計画書](feature-improvement-plan-2026-10.md)の第5〜7章を、この機能の実装計画として具体化した。以前の案と現在のコードが異なる点は、本書の「現状」を基準にする。その他の機能計画は置き換えない。

目指す体験は次の流れ。

1. 設定で「メールから予定を探す」を有効化し、初回は過去30日分を確認する。
2. ホームの「確認待ち」に「説明会の予約が見つかりました」などが出る。
3. メールの根拠と日時・場所を見て、不足項目を補って登録する。
4. 次からは新着分を確認する。同じ予約の再通知は増やさず、変更・取消は差分を提案する。
5. 承認した予定だけ、既存のGoogleカレンダー連携へ渡す。

**AIは候補の分類と抽出を担当する。重複判定の確定、保存、給与計算、カレンダーへの反映はアプリ側で管理する。** ジャックスの重複と同じく、表記の似ているものを無条件に同一扱いしない。メール・提案・登録先の対応関係をIDで残す。

## 3. 初版の対象と判定

| メールの内容 | 提案する扱い |
| --- | --- |
| 予約完了、説明会の予約確定、面接日時の確定 | 予定の追加候補 |
| 単発バイトの採用・勤務確定、集合案内 | シフト候補。集合時刻と勤務開始を分けて表示 |
| 申込受付、抽選待ち、候補日への回答依頼 | 要確認。予約済み・勤務確定にはしない |
| 同じ予約のリマインド | 既存の提案／予定に根拠を追加。新しい予定を増やさない |
| 日程・会場・勤務時間の変更 | 変更前後を表示する変更候補 |
| キャンセル・開催中止・勤務取消 | 対象を示す取消候補。承認前には削除しない |
| 募集広告、未申込の説明会案内、一般的なキャンペーン | 通常の登録候補から除外。「対象外の履歴」から見直せる |
| カード利用・銀行引落・入金通知だけ | 予定提案の対象外。既存の支払い取り込みに任せる |
| 予約と料金の案内が同じメールにある | 予約部分を対象にする。金額を自動で支出・入金へ登録しない |

初版の自動読み取りは日本語のプレーンテキスト／HTML本文。英語・海外時刻・複雑な繰り返しは要確認とする。画像・PDF・ICSだけに詳細がある場合は「添付に詳細あり・未解析」を残す。本文が空でも「予定なし」と確定しない。添付の自動解析は次版。

現在時刻とタイムゾーンは解析開始時に固定する。日付・曜日の不一致、年のない日付、複数候補日、曖昧な「来週」、終了時刻不明は確認事項にする。メールの送信日時・受信日時・引用部分を区別し、引用内の古い日時を最新の予定として採用しない。

## 4. 画面と操作

### 設定：メールから予定を探す

- ON/OFF、接続中のGoogleアカウント、AIの送信先、対象期間を表示する。
- 「過去30日を調べる」「新着を確認」「途中から再開」「解析を停止」を用意する。
- 初回に、送る項目、保存する項目、料金上限、停止・削除方法を説明する。シフト画像のAI利用設定だけではメール送信を有効にしない。
- 送信元の除外を設定できる。除外した範囲は件数に含めて表示し、「全部確認済み」と見せない。
- 「この端末で自動確認」を設ける。初期値は手動で、希望時に起動・前面復帰の自動確認をONにする。

### ホーム：確認待ち

既存の最大3件程度の表示と「すべて見る」を使う。入出金の確認を埋もれさせず、直近の取消・変更を見つけやすくする。並び順はAppStateで決め、画面ごとに別の優先度計算を持たせない。

表示例（架空の内容）：

> 説明会の予約が見つかりました  
> 11月12日 14:00〜15:30／オンライン  
> 根拠：「ご予約が確定しました」  
> ［内容を確認］

### 提案詳細

タイトル、日時、場所、オンライン参加URL、送信元、受信日、短い根拠、元メールを開く導線を表示する。「AIの正確さ95%」のような数値は出さず、「終了時刻が未記載」など確認理由を出す。

操作は「予定として登録」「シフトとして登録」「編集」「保留」「今回は登録しない」。変更・取消には対象予定と変更前後を並べる。複数候補があるときは対象を本人が選ぶ。

- 終了時刻が不明な時間指定予定は、本人が補うまで登録を完了させない。終日への変更は本人が選ぶ。
- シフトは勤務先、勤務開始・終了、休憩、適用する給与条件を確認する。休憩不明を勝手に0分にしない。
- 日給・一勤務あたり報酬だけのメールを時給へ自動換算しない。現行の給与モデルに合う勤務先設定が必要。未対応なら通常の予定として残せる。
- 元メールや参加URLは本人が押したときだけ開く。AIが返したURLも検証し、危険なスキームを拒否する。
- 狭い画面の詳細・選択には `showAppSheet` を使う。入力中の下書きは再読込で失わない。

確認待ち一覧には「新規／変更・取消／保留／履歴」を設け、検索できるようにする。「対象外の履歴」から1件を再解析する入口も用意する。

## 5. 取得・解析の流れ

```text
Gmail（端末の既存認証）
  → 予定専用の取得ジョブ／共有の通信キュー
  → MIME復号・HTMLから本文抽出・添付の有無確認
  → 端末で除外設定と解析済み記録を照合
  → AI解析（分類＋構造化抽出）
  → アプリ側で日時・根拠・重複候補を検証
  → ScheduleSuggestionとして保存
  → ホームで確認・編集・承認
  → AppStateで予定／シフトへ登録
  → 保存完了後、Googleカレンダーへ同期
```

### 取得期間と再開

- 初回は実行開始時点から過去30日間の受信メール。開催日は30日より先でも対象にする。
- 受信トレイだけでなくアーカイブ済みも含む。迷惑メール・ゴミ箱・下書き・送信メールは既定で除外する。自分宛て送信を対象にしたい場合は手動選択で扱う。
- Gmailの検索日付はタイムゾーンに注意が必要なため、開始・終了をUnix秒で指定し、取得後も `internalDate` で境界を検証する。[公式の検索仕様](https://developers.google.com/workspace/gmail/api/guides/filtering)
- 初回はキーワード検索だけで絞らず対象IDを列挙する。予約語がない集合案内や、広告に見える送信元の確定メールを落とさない。
- 新着確認は最後の完了地点から24時間重ねて取得する案。長期間開かなかった場合も空白期間を飛ばさず、量が多ければ分割して続ける。
- 各ジョブの期間上限は開始時に固定する。ページの取得途中で新着が来ても、今回と次回の境界を追跡できるようにする。
- ID一覧、処理済みID、失敗ID、ページ継続情報を保存。ページ継続情報が無効なら同じ固定期間を再列挙し、保存済みIDで重複排除する。
- 一覧の上限・本文取得失敗・未解析が残ったら完了地点を進めない。成功済み候補は表示できるが「一部未完了」と明示する。

### 本文とAI入力

件名、送信元情報、受信／送信日時、必要な本文を送る。送信元名だけでは本人の予約とは断定しない。ISO-2022-JPを含む文字コード、HTMLの表、引用の境界、改行をテストする。HTMLの画像・追跡URLを解析のために読み込みに行かない。

署名や引用を整理しても、変更前後・取消・確定の根拠を消さない。認証コード、カード番号など予定に不要な情報は送信前に除く。除去できたことを匿名化の保証とはしない。予約識別子は端末で保持し、必要なら一時的な置換記号でAIに渡す。

1通から複数の予定を抽出できるJSON配列を返す。主な項目は `kind`、`reservationStatus`、`action`、`title`、`start`、`end`、`allDay`、`timeZone`、`location`、`url`、`evidence`、`missingFields`、`relatedEventHints`。日付不明を現在日時で補わない。

Geminiの構造化出力を使い、アプリ側でも型・範囲・実在日・時刻順序・根拠の存在を検証する。JSONの形式が正しくても予定の正しさは保証されない。[構造化出力](https://ai.google.dev/gemini-api/docs/structured-output)

本文上限超過は分割解析し、全分割が成功するまでそのメールを完了にしない。分割結果の矛盾や統合失敗は要確認。初期の処理上限案は1回50通、同時AI要求1件。上限・費用見積もりは匿名サンプルで実測して調整する。すべて処理し終わるまで複数回「続ける」が必要な場合は残件数を表示する。

### 通信の分離

予定用の `ScheduleMailSource` を追加し、実際のGoogle認証・APIアクセスは `gmail_service.dart` に集約する。新しいGmail認証クライアントを別ファイルで作らない。

現行の `_throttled` は支払い取得と共有する。予定用にもう1つ30回/秒のキューを作らない。`lastFetchFailures` 等の共有カウンターを予定ジョブが上書きしないよう、取得結果に失敗ID・打ち切り状態を持たせる。支払い側の「1件でも失敗したら反映しない」は維持する。

予定用の解析キャッシュは支払い用 `_cacheKey` と分離し、アカウント＋メールID＋本文ハッシュ＋抽出仕様版で管理する。モデル・プロンプト版も記録する。本文ハッシュを調べるためだけに毎回全メールを再取得せず、取得済みメールの再解析・仕様変更時に使う。解析版の変更でも承認・却下履歴を消さない。

## 6. 重複・変更・取消の扱い

| 状況 | 判定と動作 |
| --- | --- |
| 同一メールを再取得 | アカウント＋メールIDで入口を止める。再解析しても同じ候補を更新する |
| 同一予約の別メール | 予約ID、主催者、スレッド、日時・場所を照合する。スレッドID単独では同一予約としない |
| 名前が少し違う | 類似名は候補にする材料。名前だけでは統合しない |
| 一通に複数回の勤務・複数予約 | 予約／開催回ごとに分ける。AIの出力配列の順番だけを恒久IDにしない |
| 手入力の予定と似ている | 「登録済みのこの予定と同じ？」を出す。確認後に登録先IDへ紐づける |
| 画像から登録したシフトと同日時 | 勤務先と時間を照合し、既存シフトへの紐づけを提案。二重登録を防ぐ |
| 日時変更で旧日時が消えた | 日時を予約の唯一のIDにしない。強い識別子で関連付ける。曖昧なら本人が対象を選ぶ |
| 取消だけ届いて元メールが30日外 | 保存済みの対応関係から探す。見つからなければ「取消対象を確認」で止める |
| 却下後に同じリマインドが届く | 同一予約の同一内容は再提案しない。日時等の意味ある変更は別の変更候補にする |
| 予定を手動削除した後に再受信 | 削除・解除の記録で復活を防ぐ。本人が明示的に再登録できる入口を残す |
| 承認後、本人が予定を編集 | 提案作成時の版と比較。古い提案で新しい手編集を上書きしない |

AIが示す関連候補IDはアプリ内の実在する候補に限定して検証する。抽出した値の根拠がないときは、確定情報として扱わない。メール中の指示文は解析対象のデータであり、アプリへの命令として実行しない。

変更・取消は承認済み予定に対する別の提案として保存する。通常の登録候補は開催終了後に期限切れにできるが、登録済み予定に関係する変更・取消を「過去だから」と黙って捨てない。

## 7. データと保存

| データ（名称案） | 主な項目 | 保存先 |
| --- | --- | --- |
| `ScheduleSuggestion` | ID、accountKey、元メール参照、予約の識別情報、内容の版、追加／変更／取消、抽出結果、根拠、確認事項、状態、対象予定ID、対象の期待版 | AppStateの保存・JSON・Drive |
| `MailEntityLink` | 予約／開催回の安定ID、関連メールID群、登録先の種別とID、承認した版、手動削除・却下の記録 | 同上 |
| `MailAnalysisRecord` | メールID、本文ハッシュ、解析仕様版、対象外理由、成功／失敗／未対応、再試行時刻 | 端末別・アカウント別キャッシュ |
| `MailScanJob` | 固定期間、列挙／取得／解析の進捗、未処理・失敗ID、最後の完了地点、状態 | 端末別・アカウント別 |
| `CalendarSyncOperation` | アカウント、カレンダーID、登録先ID、操作ID、対象の版、追加／更新／削除、再試行状態 | 永続化。本文ではなく登録済みデータへの参照を基本にする |
| `MailApprovalJournal` | 承認する提案の版、登録先ID、適用する変更、処理段階 | 端末内。中途保存の復旧用 |

提案の状態は `pending / held / approved / rejected / expired / superseded`。解析の成功・失敗と提案の承認状態を別にする。日時不足などは確認事項で表し、承認不能な理由を表示する。

`ShiftData` に固定 `id` と由来参照を追加する。旧シフトは起動・import時に一度採番して保存する。`updateShift` でIDを維持し、同じIDの移動・取消ができるようにする。別端末が旧バックアップから独立に採番したケースは、Drive同期と候補照合で整理し、同じIDになると仮定しない。

`EventData` の既存IDを再利用し、メール由来の新規登録には予約の安定IDから決めた登録先IDを使う。再送・再承認・画像との重複確認でIDが変わらないことをテストする。予約を区別できない場合は安定IDを推測せず、初回の確認で対応を保存する。

### 承認の途中で落ちても二重登録しない

AppStateに `approveScheduleSuggestion`、`rejectScheduleSuggestion`、`holdScheduleSuggestion` を設ける。UIから既存の追加メソッドと提案状態更新を別々に呼ばない。

承認は、対象の版を再検証→復旧用ジャーナルを保存→登録先をIDでupsert→提案・対応関係・同期操作を保存→保存成功後に通知／外部同期、の順にする。失敗を成功表示しない。現行の複数SharedPreferencesキーへの保存をトランザクションと見なさず、起動時にジャーナルを再適用できるようにする。書込失敗・容量不足も検出する。処理途中はDrive自動pushを止める。

未承認の候補はシフト・収入・残高・予定表に加えない。承認後のシフト給与は勤務先設定を使ってAppStateが計算する。メールに書かれた支払予定額をそのまま家計へ足さない。

### アカウント・端末をまたぐとき

表示中のメールアドレスだけで実行中の処理先を判断しない。接続アカウントを確認し、安定した `accountKey` を取得する。変更時は進行中ジョブをキャンセルし、古いアカウントの応答を適用しない。アカウント不明の状態では新しい解析を開始しない。

提案・対応関係・却下記録はJSON／Driveにも含める。APIキー、トークン、メール全文、実行途中のジョブは含めない。古いバックアップでは空の既定値を使う。インポートは置き換えであり、消えた提案をマージして復活させない。アカウントの違う提案を現在のカレンダーへ送らない。

複数端末運用時は承認前にDriveの最新状態を確認し、競合中は承認・カレンダー書き込みを待つ。オフラインでは下書き編集まで可能にする。Driveを使わない運用は1端末での承認を前提とする。

ただし現行のDrive同期には端末間の排他ロックがない。同期確認だけで同時承認が完全に防げるとは扱わない。初版の自動解析・承認は主端末を基本とし、安定IDと競合検出を併用する。複数端末での厳密な同時承認保証が必要なら、別途サーバー側に版付きの承認台帳を追加する。

## 8. Googleカレンダー連携

専用カレンダー「ポケットメイド」への一方向同期を使う。提案中の予定は書かない。参加者の招待やメール返信は行わず、本人用の予定として作る。

メール由来の操作には保存済みの同期キューを設け、登録成功とカレンダー同期成功を別表示する。通信失敗時は「登録済み・カレンダー同期待ち」とし、再承認を要求しない。

必須の変更点：

- 新規予定には決定的なカレンダーイベントIDを使い、通信の応答を失っても同じIDで再確認する。APIが許す文字種・長さに変換し、衝突時は登録元の識別情報を確認する。[CalendarイベントIDの仕様](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert)
- 更新の401／403／429／5xxを新規作成へ変換しない。404など対象不在を確認した場合だけ、復旧方針に従って扱う。
- 削除の404は完了にできるが、通信障害や権限不足は削除待ちとして残す。現在の例外全握りつぶしを改める。
- 古い追加応答が取消の後に返ってきても予定を復活させない。操作の版を確認して必要な後処理を行う。
- 開始・終了が未確定なメール予定を、現在の「1時間に補う」経路へ渡さない。終日の終了日はAPI側の排他的な終端へ正しく変換する。
- カレンダーIDとイベントIDをアカウントに紐づける。アカウント変更時にインメモリのカレンダーIDも破棄・再確認する。
- 既存の手入力予定・画像シフト・給料日通知への影響を回帰テストする。

Google側で手動編集された内容を逆輸入する機能は初版に含めない。別のカレンダーに同じ予約がある場合の横断重複検出も次版とし、確認画面で登録済みか確認できるようにする。

## 9. AIの接続方式・費用

**本格運用の推奨は、有料扱いのGemini APIを使う認証付き解析サーバー。** Gmail取得は端末で行い、解析に必要な内容だけをサーバー経由で送る。家計DBやGmailトークンをサーバーへ移す計画ではない。

| 方式 | 位置づけ |
| --- | --- |
| 本人のキーで端末から直接呼ぶ | 現在の画像解析方式。少量評価では流用しやすいが、共有の秘密キーや端末間共通の利用制限は置けない |
| 認証付き解析サーバー | 本格運用の推奨。サーバー認証、許可ユーザー、回数・容量上限、鍵管理が追加作業になる |
| AIを使わない定型抽出 | 費用・送信設定が決まる前の評価用。対応書式が限られることを表示する |

以前の計画はサーバー方式、現コードは本人キーの直接方式なので、ここは未確定事項として明示する。AI呼び出しは `ScheduleAnalyzer` のインターフェースに切り出し、モック／直接方式／サーバー方式を差し替えられるようにする。実メールを送る前に採用方式を確定する。

Googleは本番クライアントへの秘密キー埋め込みを避け、サーバー経由での呼び出しを案内している。本人が入力するキーと、アプリ配信物に共通キーを埋め込むことは区別する。[キーの管理](https://ai.google.dev/gemini-api/docs/api-key)

Geminiの無償サービスには機密・個人情報を送らないという条件がある。有料サービスでは入力・出力を製品改善に利用しない一方、安全対策等のための限定的保持がある。日本での実メール解析は有料扱いのプロジェクトを前提にし、「保存されない」とは説明しない。[データ利用条件](https://ai.google.dev/gemini-api/terms)

サーバー方式では、Gmailトークンがあることだけをサーバーのログイン認証にしない。検証済みの本人認証と許可ユーザー制限を設ける。認証方式・ホスティング先は着手時に選定し、CORSやURLの非公開性だけで制限しない。

モデルは固定名を計画に焼き付けず、利用可能なモデルで日本語メールの精度・待ち時間・料金を比較する。評価結果とモデル／プロンプト版を保存する。月額は次の実測で決める。

`新規解析数 × 平均入力トークン × 入力単価 ＋ 出力トークン分 ＋ 再試行分 ＋ サーバー費用`

設定に回数上限と利用状況を出す。予算通知だけに頼らず、要求前に上限を予約・判定し、上限到達なら次の送信を止める。ブラウザだけの上限は端末をまたいで保証できないため、サーバー方式ではユーザー単位で集計する。モデルや価格が変わった場合の金額は概算と表示する。

402・権限不足・キー不備は自動再試行し続けない。429・一時障害は間隔を空けて上限回数付きで再試行する。課金エラー時に実メールを無料枠へ自動で切り替えない。

## 10. 自動実行・データ管理

自動確認ONの場合、起動／前面復帰時に前回成功から6時間以上経っていれば新着確認する案とする。短時間の復帰連打、同一タブの連続実行、同じブラウザの複数タブでジョブを重ねない。タブ間のロックは停止・異常終了から復旧できる期限付きにする。

アプリを閉じている間の常時監視・Web Pushは初版に含めない。ブラウザのアクセストークン運用を前提とし、期限切れは既存の再連携へ誘導する。閉じた状態で動かすには別途、サーバー側のGmail認証・定期実行・通知配信が必要になる。

メール全文は長期保存せず、解析中のメモリを基本にする。提案には短い根拠と元メール参照だけを残す。履歴の詳細は予定終了から90日を目安に整理する案とし、重複防止・却下・削除の最小記録は本人が初期化するまで維持する。保存期限の初期値は実装時に画面説明と揃える。

設定には「自動解析を停止」「未承認提案と解析履歴を削除」「再提案防止記録も初期化」を分けて用意する。承認済み予定の削除は別操作にする。処理停止・削除後に遅れて返ったAI応答を保存しない。

Gmailの読み取り権限は既存の `gmail.readonly` を使う。AIへの送信内容・用途の説明は更新が必要。制限付きスコープのデータをサーバー経由で扱う場合の検証・評価と、個人利用等の例外条件は公開範囲に合わせて確認する。OAuthの公開状態をこの計画だけで変更しない。[Gmailスコープ](https://developers.google.com/workspace/gmail/api/auth/scopes)、[Workspaceデータポリシー](https://developers.google.com/workspace/workspace-api-user-data-developer-policy)
