# 設計方針と移行計画（2026-11-19 起案）

前提となる調査結果は `docs/survey.md`。ここでは「何を変え、何を残し、どの順で、どう確かめるか」を決める。
GPT による設計レビューの前の版。レビューの指摘への回答は末尾の「レビュー対応」に追記する。

## 1. 目的

- 1 か所を直すと別の画面の金額が静かに変わる、を構造で起きにくくする
- 既存の保存データ・計算結果・Google 連携・Web/iOS の差を壊さない
- 残高・予想・根拠・次の引き落とし・状態を、迷わず読める画面にする

速さより根拠と安全性を優先する。全面書き換えはしない。

## 2. 維持するもの

| 対象 | 理由 |
|---|---|
| サーバー無し・SharedPreferences・Drive の appDataFolder | CLAUDE.md の構成。変更の必要が無い |
| 保存キー（`flutter.saved_*`）と JSON の形 | 既存端末・ドライブ上のデータとの互換 |
| `AppState` を画面の唯一の窓口にする（`context.watch<AppState>()`） | CLAUDE.md の「画面は計算しない」。provider の使い方も変えない |
| AppState が外部サービスを import しない向き（`CalendarSyncHook`） | 依存が一方向で循環が無い |
| `gmail_sync` の全か無かの反映、`decideSyncState`、`importJson` の巻き戻し、認証の復帰手順 | 過去の不具合から作られ、テストがある |
| 墓石・変換済み・メモ・付け替え・別名の記録 | CLAUDE.md の「消えたり戻ったりしないための記録」 |
| 金額計算の既存の規則（n-1 月、ゲート、締め期間、合算、確定優先、一度きり） | 仕様。計算の中身は動かさず、置き場所と呼び方を整理する |
| `GmailService` の解析規則・キャッシュのバージョン | 実メールでの検証済み。今回は解析を変えない |

## 3. 変えるもの（要点）

1. **予想残高を 1 つの「月の予想」から作る**（7 か所の式を 1 か所に）
2. **引き落とし日・締め期間の規則を純粋関数に集める**（`lib/finance/billing_dates.dart`）
3. **旧系統の支出計算（`cardChargesOf` など）をやめ、画面の支出をすべて予想と同じ規則に**（B3・B4）
4. **時刻を注入できるようにする**（`AppState(clock: ...)`）。月境界のテストを書けるように
5. **保存の往復を全項目テストで守り、取り込み後もカード設定を保存する**（B1）。起動時と取り込み時の自己修復を共通化（B8）
6. **データ型を `lib/models/` へ分ける**（`app_state.dart` から export するので、既存の import はそのまま）
7. **UI: 共通の見た目の決まりと少数の部品を作り、ホームを「残高 → 予想 → 根拠 → 次の引き落とし → 確認待ち」の順に組み直す**

## 4. 新しい責務分担と依存の向き

```
screens/ widgets/ ──(読む・操作する)──> AppState ──> finance/（純粋な計算部品）
        │                                  │  └──> models/（データ型・JSON）
        └─> ui/（見た目の決まり・共通部品）    │
                                           └── CalendarSyncHook（実装は google_calendar_sync）
gmail_sync / drive_sync / google_calendar_sync / mail_schedule_service ──> AppState, GmailService
```

| 層 | 置く場所 | 責務 | してはいけないこと |
|---|---|---|---|
| データ型 | `lib/models/*.dart` | 形と JSON の読み書き、その型だけで決まる計算（シフトの給与、ローンの回数など） | 保存・通知・他の型の参照による集計 |
| 計算部品 | `lib/finance/*.dart` | 日付規則（営業日・締め期間・引落日）、月の予想の型 | `DateTime.now()`、SharedPreferences、Flutter の UI |
| 状態 | `lib/app_state.dart` | 全データの保持、変更操作（保存＋通知）、画面に出す計算の入口、自己修復、保存・読込 | 外部 API の呼び出し、画面の文言・色の決定（※移行中は残る） |
| 外部連携 | 既存の `gmail_service` などのファイル（場所は変えない） | 認証・API・解析・同期の手順 | 金額の計算 |
| 見た目 | `lib/ui/*.dart` | 色・文字・余白の決まり、金額や状態の表示部品 | 計算・データの保持 |
| 画面 | `lib/screens`・`lib/widgets` | 表示と入力、AppState の呼び出し | 金額の合計・規則の判定 |

💡 CLAUDE.md の「全データ・全計算は AppState」は、**画面から見た窓口が AppState** という意味で守る。
`finance/` の純粋関数は AppState が呼ぶ部品で、画面からは直接呼ばない。
この解釈を CLAUDE.md に書き足してよいか確認したい（§9 の Q5）。

### 月の予想（`MonthForecast`）

```dart
enum Certainty { confirmed, scheduled, estimated } // 確定 / 予定 / 見込み
enum ForecastKind { income, transfer, draw, oneTime }

class ForecastLine { // 予想の 1 行（日付つき）
  final ForecastKind kind;
  final String label;      // 画面に出す名前（例: 楽天カード、カフェ、動画配信）
  final String group;      // まとめ表示用（例: 定期支払い）
  final int amount;        // 入金は +、出金は −
  final DateTime date;     // 入金日・引落日
  final Certainty certainty;
}

class MonthForecast {
  final DateTime month;
  final int start;               // 月初の起点（今月は「残高−未反映デビット＋財布」、翌月以降は前月末）
  final List<ForecastLine> lines;
  int get end => start + lines.fold(0, (s, l) => s + l.amount);
}
```

- `AppState.monthForecast(offset)` が、今の `incomeForecastIn`・`transfersForecastIn`・`drawBreakdownOf`（定期は 1 件ずつ）・
  `oneTimeExpensesIn` から**行を作るだけ**。足し引きの規則はこれまでの関数のまま
- `thisMonthBalance`・`nextMonthBalance`・`monthAfterNextBalance`・3 つの内訳・`cashEventsAhead` は、すべてこの行から作る
- 確定／予定／見込みの付け方:
  - 確定 … 銀行の引落確定があるカード月の引き落とし、実給料を入力した月の給料
  - 予定 … 自分で登録した定期・ローン・予定入金・予定支出・頭金、メールで分かった PayPay の出金
  - 見込み … シフトから推定した給料、利用通知・請求予定から推定したカードの引き落とし
- 予想の数字は変えない。移行の前に「時刻を固定した合成データで、今の実装が出す金額」を固定し（§7 の段階 1）、移行後も一致させる

### 引き落とし日の規則（`finance/billing_dates.dart`）

```dart
DateTime clampedDay(int year, int month, int day);
DateTime cardDrawDate({required int paymentDay, required DateTime payMonth}); // 休みなら翌営業日
({DateTime start, DateTime end}) closingPeriod({required int closingDay, required DateTime payMonth});
DateTime payMonthOfUsage({required int closingDay, required DateTime usageDate});
```

AppState の `cardDrawDateOf`・`drawDateOf`・`cardClosingPeriodOf`・`drawDateForUsage`・`subscriptionDrawsIn`・`pendingDraws` はこれを呼ぶ。
`nextBusinessDay` などは `japanese_holidays.dart` のまま使う。

### 保存

- `saveData` がカードの引落日・締め日も書く（B1）。`_saveCardPaymentDays` は同じ書き込み関数を呼ぶ
- 「全項目を埋めたデータ」で次の往復を固定するテストを足す:
  書き出し → 取り込み → 書き出し が一致／保存 → 読み込み → 書き出し が一致。項目を足して片方を忘れると落ちる
- 自己修復を `_repairData()` にまとめ、読込と取り込みの両方で呼ぶ（B8）。2 回目は何も変えない（冪等）ことと、
  直すものが無ければ保存しないことをテストする
- `_migrateWorkplaces` はシフトの `id`・`calendarEventId` を引き継ぐ（B2）。既に ID が変わってしまった過去の分は元に戻せない（手掛かりが残っていない）

### ドライブ同期

- `pushNow` は時刻を取ってから書き出す（B7）。テストのため、アップロード関数を差し替えられる入口を 1 つ足す
- 判定（`decideSyncState`）・競合時に選ばせる流れは変えない

## 5. 互換性

| 項目 | 方針 |
|---|---|
| 保存キー・JSON | 変えない。新しいキーは足さない予定（足す場合は読込側で既定値を持つ） |
| 書き出しファイル（`version: 1`） | 変えない。古いアプリで書いたファイルも、新しいアプリで書いたファイルも互いに読める |
| 予想残高の数字 | 変えない（段階 1 の固定テストで確認）。変える場合は §9 で個別に確認したものだけ |
| 画面の「支出」の数字 | B3・B4 の修正で変わる（§9 の Q1・Q2） |
| 確認待ちの引き落とし予定 | 金額・日付が予想と同じ規則になる（Q3）。ID（`card:カード:年月` など）は変えないので、処理済みのものが再び出ることは無い |
| ドライブ上のデータ | 形は同じ。B1 の修正後、取り込んだカード設定が正しく保存される |
| Web と iOS の差 | `kIsWeb` 分岐・条件付き import は触らない。iOS はこの環境でビルドできないので未確認と報告する |

## 6. UI/UX の方針

### 決まり（`lib/ui/`）

- 色: ブランドのピンク（`Colors.pink` を種にした `ColorScheme`）は維持。意味の色を名前で持つ
  （入金・出金・注意・確定・見込み）。**色だけで区別しない**: 金額は `+`/`−` と言葉、状態は「確定」「見込み」の文字
- 文字: 本文 14、補足 12 を下限（現状 10〜11 の箇所がある）。金額は大・中・小の 3 段
- 余白: 4 の倍数（4/8/12/16/24）。カードの角丸は今の 18 を維持
- 押せる大きさ: 48×48 以上
- 部品は用途がはっきりしたものだけ作る:
  `MoneyText`（符号・桁区切り・色・読み上げ用の文言）、`CertaintyBadge`（確定／予定／見込み）、
  `StatusBanner`（状態と次の操作のボタン）、`SectionHeader`

### ホームの組み直し（スマートフォンを先に）

```
┌ ホーム ──────────────── 🔔3 ┐
│ [同期の状態バー] メールを確認しました 9:12 ・詳細   ← 失敗・未連携ならボタンつき
│ ┌ いまの残高 ─────────────┐
│ │ 口座 ¥85,000   11/16 に更新（3日前） [更新] │
│ │ 財布 ¥3,000                         │
│ └──────────────────────┘
│ ┌ 月末の見込み ───────────┐
│ │ 11月末 ¥112,730  (タップで根拠)        │

│ │ ⚠ 最も少なくなる日 12/10 ¥12,000        │
│ └──────────────────────┘
```

- 「根拠」シート: 月初の起点 → 入金（日付・確定/見込み）→ 引き落とし（日付・確定/見込み）→ 一度きり → 月末。
  行の合計が月末の金額に一致する（同じ `MonthForecast` から作る）
- 削除する表示: ホームの「収支の内訳」グラフと、旧系統の「カード請求(未払い)／定期支払い／分割払い(今月)／ATM」の行、
  2 か所目の「現在の残高」。**機能は消さない**: 入金・引き落とし反映・予定入金・予定支出・入出金の履歴・財布は「お金の操作」に移す。
  年間サマリーは「収支の履歴」画面に移す（ホーム右上のボタンから今までどおり開ける）
- 0 円の行は出さない
- PC 幅（840px 以上）では、左に残高と見込み、右に次の引き落とし・確認待ちの 2 列
- 状態の表示: 読み込み中・未連携・同期の競合・取り込み失敗・空の状態を `StatusBanner` に揃え、それぞれ次に押すボタンを付ける
- 確認の扱い: 削除・全置換・残高の書き換えは今の確認ダイアログを維持。新しく作る操作も同じにする

### 他の画面

- 支払い: 合計と「分割を足すか」の判定を AppState に移す（見た目はほぼ同じ）。チップの文字を 12 以上に
- 設定: 開発用（見本の提案、🔧）を「詳細設定」の中へ。動かない「三井住友銀行 連携設定（未連携）」は消す（Q4）
- 履歴: 月ごとの支出を予想と同じ規則（`expenseBreakdownOf`）に（Q1）
- カレンダー: 印の凡例に加え、日付を選んだときの一覧で種類を文字で出す（今の一覧を確認してから）

## 8. 採用しなかった案

| 案 | 採用しない理由 |
|---|---|
| Riverpod・Bloc などへの移行 | 依存の追加と全画面の書き換えが要る。今の provider + ChangeNotifier で困っているのは「計算の重複」で、状態管理の仕組みではない |
| AppState を複数の ChangeNotifier（支払い用・シフト用…）に分割 | 予想はほぼ全データを読むので、分けると相互参照と通知の順序の問題が増える。保存も 1 回でまとめて書いている |
| リポジトリ層・インターフェースを全面導入 | 外部連携は既に `GmailSyncSource`・`CalendarSyncHook` で必要な所だけ差し替えられる。層を増やしても今の不具合は減らない |
| 保存を 1 つの JSON にまとめる（キーを統一） | 既存端末のデータの移行が必要になり、失敗時のリスクが大きい。往復テストで食い違いを検出すれば足りる |
| 予想の結果をキャッシュして速くする | テストは項目を直接書き換えるので、キャッシュが古いまま残る危険がある。遅いという実測も無い |
| AppState の残りのメソッドを `part` ファイルへ機械的に分割 | 差分が非常に大きくなり、レビューで「移動しただけ」かを確かめにくい。責務が独立した部分（データ型・日付規則・予想）だけを分ける |
| Flutter 3.47 以降の `material_ui` パッケージへの移行 | パッケージの追加と全ファイルの import 変更が要る。今は非推奨の予告（info）だけで動作に影響しない。別の作業として扱う |

## 10. 判断に迷っている点
