## P1: 保存中のカード設定変更が古い値で上書きされる

対象: `lib/app_state.dart:4391-4397`、`_persistedValues`、`_writeValues`。

今回、通常の全データ保存にカード設定も含めた一方、設定変更は従来の `_writeCardDays` から直接 SharedPreferences に書くままになっている。この経路は `_enqueueWrite` の直列化を通らない。

画面上は26日でも次回起動で27日に戻り、予想残高やカレンダーの日付が変わる。カード削除・締め日変更など同じ経路も対象に、更新時刻と保存の直列化を統一する必要がある。復旧用の一時記録が新しい設定を巻き戻さないことも検証する。

## P1: Drive取り込みの保存中に行った編集が同期済みになる

対象: `lib/drive_sync.dart:389-390`。

`await app.importJson(...)` のあと、完了時点の時計を `driveSyncedAt` にしている。取り込みの非同期保存中にも通常の編集が可能なので、その編集はリモートに存在しないのに同期済みになる。取り込み前の `basedOn` チェックではこの時間帯を保護できない。

再現: リモート残高2000円を取り込み、永続化を待機 → 時計を1秒進めてローカル残高3000円を保存 → 取り込みを完了。期待 `localNewer`、実際 `upToDate`。ローカルには3000円、リモートには2000円が残る。

取り込み対象のローカル更新世代と、取り込み開始後の編集を区別するか、取り込み全体を排他処理にする。完了時刻までの変更を一括して同期済みにしない。取り込み中の通常保存、失敗時の巻き戻しとの競合も確認する。

## P2: SharedPreferencesのfalseによる失敗を成功扱いする

対象: `lib/app_state.dart:5127-5149`、`_writeValues` と復旧処理の `remove`。

保存APIの戻り値は `Future<bool>`。現在は例外のみを失敗として扱い、`false` を無視している。復旧点を書けなくても本体の上書きを開始でき、保存や記録削除の失敗後に成功扱いにできる。

再現: ストアの `setValue` を例外ではなく `false` で失敗させる。`importJson` が `StorageWriteFailure` を投げることを期待するが、実際は正常終了する。

すべての保存・削除でboolを検証し、falseも失敗処理へ渡す。復旧点、一時記録、本体の途中キー、記録の削除で個別に検証する。この再現は偽ストアによるAPI契約上の失敗であり、実ブラウザの容量不足が必ずfalseを返すという意味ではない。
